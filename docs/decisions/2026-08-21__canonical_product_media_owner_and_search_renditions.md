# Decision: canonical product media owner and search renditions

**Decision ID:** `FP-WEB-ADR-2026-08-21-001`
**Date:** `2026-08-21`
**Status:** `accepted`
**Scope:** product media processing, storage, search derivatives, deletion lifecycle, structured data

## Context

Product images are database-owned business media under `userfiles/goods/`. Search visibility work required stable aspect-ratio variants without creating a second product catalog, duplicating path rules, fabricating imagery, or making future uploads depend on manual maintenance scripts.

The project also has two runtime layouts:

- local repository webroot: `base/`;
- production webroot: deployment contents without the local `base/` prefix.

A repository-root-specific media path therefore cannot be the canonical runtime rule.

## Decision

1. `base/libraries/GoodsImageUploadOptimizer.php` is the canonical owner of product image processing and deterministic product-image derivatives.
2. Product database authority remains `goods.img` and `goods.gallery_img` with paths relative to `userfiles/`.
3. Product search renditions are deterministic filesystem derivatives and do not receive database columns.
4. The canonical search family for the main product image is:
   - `1x1` — `700 × 700`;
   - `4x3` — `700 × 525`;
   - `16x9` — `704 × 396`;
   - JPEG quality `94`;
   - centered fit/pad on white without upscaling.
5. Derivatives live under `goods/<catalog-alias>/search/` and use deterministic names derived from the canonical main filename.
6. A family is public/usable only when all three expected renditions pass the complete-family gate.
7. `structuredData.php` exposes only a verified complete family.
8. `BaseAdmin.php` generates the family automatically for future main-image uploads and cleans current-request failures/replacements.
9. `DeleteController.php` removes the family for single main-image deletion and full product-record deletion.
10. Runtime `userfiles` ownership is resolved from the deployed `libraries/` location, so the same source works in local and production layouts.
11. Historical products are backfilled through a guarded additive media migration with inventory, off-host backup, exact manifest accounting, validation, and rollback ownership.

## Rejected alternatives

### Add three database image columns

Rejected because the paths are deterministic derivatives of `goods.img`; storing them separately would create synchronization debt and a competing authority.

### Generate variants ad hoc in templates

Rejected because templates are not storage/processing owners and would duplicate path and validation rules.

### Blind crop to target ratios

Rejected because source subject placement is not consistently known. The accepted default is centered fit/pad without upscale.

### Generate three unrelated/fake images for search appearance

Rejected. Aspect renditions must remain truthful derivatives of canonical product media.

### Keep repository-root-specific `base/userfiles` runtime construction

Rejected because production deploys without the local `base/` prefix.

## Consequences

Positive:

- one product-media owner;
- no derivative database schema expansion;
- automatic behavior for future uploads;
- stable crawlable URLs;
- complete-family fail-closed behavior;
- lifecycle cleanup prevents known derivative orphans;
- local and production runtime layouts share one source implementation;
- structured data can expose multiple truthful aspect ratios without changing canonical product identity.

Costs:

- three additional JPEGs per canonical main image;
- historical rows required a one-time backfill;
- derivative lifecycle must remain synchronized with canonical main-image lifecycle;
- schema output still cannot guarantee a particular Google SERP presentation.

## Production acceptance

On 2026-08-21 the historical backfill completed with:

```text
164 canonical source images
492 exact generated renditions
66,307,706 generated bytes
492 / 492 public HTTP 200 JPEG
118 Product schema pages
118 pages with exact three search-rendition refs
354 search-rendition refs total
```

No database mutation was required.

## Follow-up governance

A future change to product-media ownership, database authority, search-profile dimensions, output format, crop/fit policy, or lifecycle semantics requires a new architecture decision rather than an undocumented local override.
